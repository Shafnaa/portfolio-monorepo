# Issue Management

Use this skill to ensure all project issues adhere to the standard structure, metadata format, and the Epic -> Story -> Task hierarchy.

## GitHub Source of Truth

- **GitHub Issues are authoritative.** Resolve the repository from the git origin remote before any GitHub MCP call: run `git remote get-url origin`, parse `owner/repo` from either SSH (`git@github.com:owner/repo.git`) or HTTPS (`https://github.com/owner/repo.git`) form, and strip the `.git` suffix. Never hardcode or guess a repository name.
- Issues are created and updated through the GitHub MCP tools (`github_issue_write`, `github_sub_issue_write`) using that resolved `owner`/`repo`, never by writing local files.
- The local `.issues/open/` and `.issues/closed/` folders are mirrors generated by `gh-issue-sync pull`. Never hand-edit mirrored files; run `gh-issue-sync pull` to refresh them.
- Hierarchy is structural: every Story is a sub-issue of its Epic, and every Task a sub-issue of its Story (`github_sub_issue_write`, method `add`). Repeat parent links in the body's `Parent:` section so relationships survive outside GitHub.
- Each issue carries exactly one type label: `epic`, `story`, or `task`.

### Metadata Mapping

The templates' YAML frontmatter describes the local mirror format produced by `gh-issue-sync pull`. When creating or updating issues on GitHub, map fields as follows:

| Frontmatter field | GitHub equivalent |
| ----------------- | ----------------- |
| `title` | Issue title |
| `labels: [epic \| story \| task]` | Issue label (exactly one) |
| `projects` | Optional GitHub project; not required by this workflow |
| `state`, `state_reason` | Issue state (open/closed); change via `github_issue_write` method `update` |
| `synced_at`, `info.*` | Managed automatically by GitHub and `gh-issue-sync`; never set manually |
| Parent reference (body section) | Sub-issue link via `github_sub_issue_write`, plus the body's `Parent:` section |

Issue bodies themselves contain no frontmatter — only the template sections below.

## Templates

Before generating any issue, refer to the standalone template files:

- Metadata (shared YAML frontmatter): `templates/metadata.md`
- Epic: `templates/epic.md`
- Story: `templates/story.md`
- Task: `templates/task.md`

Every issue body must follow the body template matching its type. The metadata frontmatter applies only to locally mirrored files; on GitHub it is expressed through the mapping above.

## Hierarchy Rules

1. **Epic:** A collection of related Stories grouped around a single feature or value stream. Label `epic`. Contains a summary plus product rationale: goals and business objectives, background and strategic fit, key assumptions, design links, an open questions and decisions log, and explicit out-of-scope items.
2. **Story:** A User Story expressed purely from the user's perspective — "As a... I want to... So that...". Label `story`. Must be free of technical implementation details.
3. **Task:** The technical implementation steps. Label `task`. Generated only after the user reviews and approves the parent Story.

## Epic Rules

Every Epic must include the following mandatory sections from `templates/epic.md`:

1. **Summary:** Concise technical overview of the value this Epic delivers to the user.
2. **Goals & Business Objectives:** Primary objective statement plus a measurable success metric / KPI. Even when minimal, both must be stated.
3. **Background & Strategic Fit:** Customer context and alignment with organizational vision; explain why this matters now.
4. **Key Assumptions:** Explicit assumptions about user behavior, technology, or business needs that influence planning. Use `[TBD]` when unknown rather than inventing values.
5. **Stories:** Links to each child Story issue.
6. **User Interaction & Design:** Links to design prototypes or user flow references.
7. **Open Questions & Decisions Log:** Items requiring a decision with owner, status, and documented resolution once decided.
8. **Out of Scope:** Explicit exclusions protecting the release boundary.

### Epic Constraints

- The Epic is a living document: update it as stories evolve or trade-offs occur.
- Do not fully specify the entire project before engineering starts, and do not require iron-clad sign-offs before beginning work.
- Epics carry product rationale only; technical implementation details belong in Stories' child Tasks.

## Story Rules

Every Story must include the following mandatory sections from `templates/story.md`:

1. **User Story:** "As a... I want to... So that..." — purely from the user's perspective, free of technical implementation details.
2. **Why This Matters:** Short product rationale linking the story to its Epic's objectives and priority.
3. **Success Metrics:** Table of metric, measurable target, and how it is measured. Even when minimal, the table must be present.
4. **Acceptance Criteria:** Given/When/Then observable outcomes.
5. **Linked Context / Artifacts:** Mandatory links to research, screenshots, design references, or related issues.
6. **Out of Scope:** Product-level exclusions (technical scope belongs in Tasks).
7. **Open Questions:** Items requiring a decision, with owner and status.
8. **Parent:** Reference to the parent Epic.

Stories must not contain implementation details; those belong in child Tasks.

## Task Rules

Every Task must include the following mandatory sections from `templates/task.md`:

1. **Technical Objective:** The specific technical outcome this Task must produce.
2. **Scope:** Explicit `In Scope` and `Out Of Scope` lists. Even when one is empty, it must be stated.
3. **Technical Constraints:** Stack, architecture, interfaces, runtime, accessibility, performance, and security requirements. Use measurable or verifiable language where possible.
4. **Implementation Steps:** Ordered list of specific implementation actions.
5. **Behavior And Edge Cases:** Expected behavior for important states including invalid, empty, loading, or failure states.
6. **Dependencies:** Parent Story, prerequisites, and consumers of this Task.
7. **Verification:** Split into `Automated Verification` (exact tests, assertions, or commands) and `Manual Verification` (user-visible behavior to check manually).
8. **Completion Boundaries:** Concrete conditions that must be met for the Task to be considered complete.

### Task Constraints

- Tasks must not introduce requirements absent from the parent Story unless those requirements are documented as implementation constraints.
- Tasks must not introduce features or files beyond the explicit `In Scope` boundary.
- Verification must use exact commands or assertions, not vague statements like "test that it works."
- A Task may reference dependencies and consumers but must not modify unrelated issues.
- Tasks should be generated only after the parent Story is approved.

## Structure & Rules

- GitHub Issues are the single source of truth; create and update them only via GitHub MCP tools.
- `.issues/open/` holds files mirrored by `gh-issue-sync pull`, named `[id]-[issue name in slug].md` by the tool (e.g., an issue titled "Epic 3: Initialize project" with ID #3 becomes `3-epic-3-initialize-project.md`). Never hand-edit these files.
- Reference rule:
  - Every Story must be linked as a sub-issue of its parent Epic, and reference it in the file body.
  - Every Task must be linked as a sub-issue of its parent Story, and reference it in the file body.
- The `synced_at` field is managed by the external sync tool; do not modify it.
- Change issue state (open/closed) through `github_issue_write` method `update` on GitHub; then run `gh-issue-sync pull` to refresh the mirror.

## Workflow

1. **Project Manager:** Compose the issue body from the matching template, create it with `github_issue_write` (method `create`) and the correct type label (`epic`, `story`, `task`), then link children to parents with `github_sub_issue_write` (method `add`).
2. **Sync:** After every create or update, run `gh-issue-sync pull` so `.issues/` mirrors GitHub.
3. **Developer Agent:** When creating Tasks for an approved Story, follow the same flow — body from `templates/task.md`, label `task`, sub-issue of the parent Story — then pull again.
